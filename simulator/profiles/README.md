# profiles

## profile_table.csv

The measured model-by-node profile table: 72 (model, node) pairs at four
object-count groups. This is the file the paper's results come from. It is
not in the public snapshot; put it here, or pass `--profiles` to `run.py`
and `sweep.py`.

Columns:

| Column | Meaning |
| --- | --- |
| `model` | detector name |
| `node` | fleet node, e.g. `orin_nano`, `pi5_aihat_a` |
| `group` | object-count group, 0 to 3 |
| `energy_mWh` | measured energy per request at the reference state |
| `mAP` | measured accuracy on the calibration sequence |
| `latency_ms` | measured end-to-end latency |

Lines beginning with `#` are ignored, so provenance tags can be carried as
comments at the top of the file.

Node names carry an instance suffix where the fleet has more than one board
of a type: `pi5_aihat_a` and `pi5_aihat_b` are two Raspberry Pi 5 + AI HAT+
nodes and both resolve to the `pi5_aihat` platform in
`driftsim/models.py`, which is where the thermal thresholds of Table I live.

## example_profile_table.csv

**Synthetic. Not measured data.** It exists so the simulator runs end to end
on a clean clone, and so `run.py --smoke` and `sweep.py --smoke` exercise
every code path without the measured table.

It is generated by `make_example_table.py` from a fixed seed, and it is
constructed to sit in the same regime as the measured table:

- six nodes, twelve detectors, four object-count groups, 72 pairs;
- a 1.62x to 1.65x energy gap between the cheapest feasible option and its
  nearest cross-device competitor, against the 1.64x the paper measures;
- every candidate inside the 150 ms latency constraint;
- an accuracy range wide enough that the static baselines separate.

Running against it reproduces the paper's qualitative results: thermal
throttling alone produces no inversions, battery asymmetry dominates over
the long horizon, the three mechanisms together invert more often than the
sum of their individual effects, greedy saves around 20% against HMG, and
the Lyapunov controller tracks every budget within about 2% while greedy
ignores it entirely.

It does **not** reproduce the paper's numbers, and it is not meant to. Its
drift is more aggressive than the measured hardware's, so inversion rates
come out roughly an order of magnitude higher, and one consequence flips:
the total inversion penalty lands above Theorem 3's break-even threshold,
so re-profiling pays for itself here where on the measured table it cannot.
The run summary's `breakeven` block prints both sides of that inequality,
so the reason is visible rather than surprising.

To regenerate it:

```
python3 profiles/make_example_table.py
```
